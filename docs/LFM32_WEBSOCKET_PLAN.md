# 第二期常驻 WebSocket 方案（未开通、未购买）

第一期不能完整记录两次轮询之间的盘口变化，也不能确认冰山、撤单和被动吸收。第二期建议单个常驻 Python 服务、SQLite WAL（小规模）或按日 Parquet 压缩原始日志，另每5m生成与本期兼容的JSON；GitHub仅接收聚合结果，不充当逐笔存储。

## 采集状态机与恢复

1. Binance spot `btcusdt@trade`（单笔撮合）与 `@aggTrade`二选一作为统计主流；另一流仅审计且不相加。持久唯一键 `(exchange,market,symbol,feed_type,id)`。Binance USDT永续另流，永不混为现货。
2. Coinbase Exchange官方 matches/full feed，明确 WS side 对 maker 的语义，按官方文档逐频道验证，不能直接复用其他 Coinbase接口字段含义；启用 heartbeat 及最后trade_id检查。成交、序列号、接收时间、事件时间均持久化。
3. Binance diff-depth：先订阅并缓冲，再取REST快照；丢弃 u≤lastUpdateId，首条覆盖 lastUpdateId+1；持续校验 U/u，出现缺口立即使簿失效、停止盘口信号，重新快照并重放缓冲。仓库已有 `BinanceBook` 最小序列检查组件，但尚无生产常驻服务。
4. Coinbase 使用官方 full/level2 对应规则，full通过快照sequence衔接且过滤相关事件；level2按官方协议重同步，不能把全市场/其他频道序列语义套用到level2。若所选频道不能证明连续性，必须降级为 unavailable，而不是宣称已校验。
5. 服务ping/pong、应用心跳和最后消息时间同时检查；连接失效、队列溢出或数据落盘失败均记录明确 gap。指数退避加随机抖动、连接/订阅配额与24h轮换、SIGTERM先落盘、systemd自动恢复；禁止重连风暴。
6. 成交可通过可用官方REST按ID回补；只在双方时间和ID连续性验证后标完整。Coinbase过去记录若超出可访问范围，或Binance历史单笔接口要求授权/受限制，不能将聚合回补伪装成单笔回补。返回 unavailable，并保留所缺ID/UTC范围。深度历史通常不能REST补回，重快照只恢复**未来**状态，断线期间流动性变化仍 unavailable。
7. 每5分钟只汇总已经闭合的完整区间，使用持久水位、来源和币种；不跨数据缺口延续CVD。写临时文件后原子替换JSON，失败时保持前次文件但读时资格自动过期。上传token最小contents权限，可独立data分支；限制重试并核对SHA。避免把每笔写入GitHub。
8. 定时独立心跳检查、磁盘水位和最新事件延迟告警；告警通道只有用户明确授权后连接，不在本次主动发消息。

## 盘口行为推断的限制

同价位数量下降可能是成交或撤单；仅增量数量差不能辨别。将可验证match事件与盘口事件时间/序列对齐，仍无法一一归因时报告“无法区分”。被动吸收须有真实主动成交冲击、价格反应与可持续补充流动性，冰山仅推断，给出观测区间、阈值和反例；买墙不当作实际买入。OI/费率与清算热力图也不证明机构身份。

## 开通验收

先测试真实断网重连/服务重启/序列丢包/重复事件/磁盘写失败，验证丢段 unavailable；再连续试运行至少7天，报告覆盖率、端到端延迟、回补成功率、真实存储增长与月费估算。冻结评分公式后积累足够历史，用前向滚动样本外检验再讨论预测用途。当前交付仅第一期与此设计，无付费服务器、无已部署常驻进程。
